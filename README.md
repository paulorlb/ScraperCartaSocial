# Collect Carta Social Data Pipeline

Collect Carta Social equipment records, prepare service and address tables,
geocode facilities, and export analysis datasets. The workflow supports all
available service types or a user-defined subset.

A service-table row represents a social service offered by an equipment
(facility). Several service rows can share an equipment identifier and location.

## Setup

Install [Miniforge](https://github.com/conda-forge/miniforge), open Miniforge
Prompt on Windows or a Conda-enabled terminal, and enter the repository.

```bash
conda config --set channel_priority strict
conda env create -f environment.yml
conda activate carta-social
python -m ipykernel install --user --name carta-social --display-name "Python (carta-social)"
```

Copy `config.example.toml` to `config.toml` and `.env.example` to `.env`.
Both local files are ignored by Git. In PowerShell:

```powershell
Copy-Item config.example.toml config.toml
Copy-Item .env.example .env
```

Run these copy commands only when the local files do not already exist.
Keep personal configuration and credentials when updating an existing checkout.

The environment specifies Python 3.12 and dependency compatibility ranges.
It is not a platform-specific lockfile. Update with
`conda env update -f environment.yml --prune` and capture exact resolved versions
with `conda env export > environment-resolved.yml`.

## External data configuration

Set `paths.data_root` in your local `config.toml`:

```toml
[paths]
data_root = "E:/path/to/ScraperCartaSocial_data"
```

Use forward slashes on Windows. An absolute path can differ on every machine.
A relative path resolves from the configuration file, independently of the
terminal's working directory. The data folder must be outside the repository.

The configured folder contains:

```text
ScraperCartaSocial_data/
├── raw/          # Source tables; collection snapshots in raw/scraping/snapshots/
├── interim/      # Tables and caches generated by the pipeline, incl. interim/scraping/<snapshot_id>/
├── processed/    # Current analysis datasets and metadata
└── archive/      # Optional retained reference data
```

Set input paths in `[inputs]`; they resolve relative to `data_root`:

| Setting | Purpose |
| --- | --- |
| `services` | Required service-record CSV |
| `equipment_urls` | Required equipment ID/URL CSV for notebook 01 |
| `url_text` | Optional text URL log to cross-check against the CSV |
| `coordinate_cache` | Optional Parquet or JSON coordinate input |
| `selection_workbook` | Optional Excel selection input |
| `service_sheet` | Service worksheet name for workbook mode |
| `address_sheet` | Equipment-address worksheet name for workbook mode |

Leave optional paths empty to disable them. The configured files must be inside
the external data root. Restart the notebook kernel after changing configuration
so that imported paths and function defaults are refreshed.

## Credentials

Store usernames, passwords, API keys, and HTTP identity in the root `.env`:

```dotenv
GOOGLE_MAPS_API_KEY=
HTTP_USER_AGENT=CartaSocialPipeline/1.0
NOMINATIM_URL=http://localhost:8080
NOMINATIM_USERNAME=
NOMINATIM_PASSWORD=
```

Notebooks 01 and 02 explicitly call `load_environment()` before reading
credentials with `os.getenv`. Existing shell variables take precedence;
`load_environment(override=True)` makes the file authoritative when required.
Paths belong in `config.toml`; credentials belong in `.env`.

Google credentials are used only when the Google provider is selected.
Optional Nominatim username/password values support HTTP Basic authentication
on a private instance. No credentials are needed for offline execution.
Neither local configuration nor credentials belong in notebooks or Git.

## Run the workflow


Select the
**Python (carta-social)** kernel and execute notebook cells in order.

| Notebook | Operations |
| --- | --- |
| `01_data_collection.ipynb` | Collect equipment into versioned snapshots, rebuild snapshot tables, and inspect service records and URL coverage |
| `02_cleaning_geocoding.ipynb` | Clean values, select service types, prepare facility addresses, and reuse/request coordinates |
| `03_geographic_export.ipynb` | Join the saved selection to coordinates and write datasets with coverage metadata |

The default is offline. Notebook 02 processes all input categories with
`service_types = None`; set a list of exact source labels for any subset.
Unknown categories raise an error. Workbook mode is optional and uses the
worksheet names from configuration.

Current processed outputs:

- `carta_social_services.csv`: complete configured service table.
- `carta_social_service_locations.gpkg`: valid point features, layer `service_locations`.
- `carta_social_dataset_metadata.json`: category counts and spatial coverage.

All outputs are written under the external data root. The
[dataset guide](docs/datasets.md) defines input fields and output contents.
The [methodology](docs/methodology.md) documents transformation and quality rules.

## Collection and geocoding

Notebook 01 stores each collection in its own snapshot folder,
`raw/scraping/snapshots/<snapshot_id>/` (UTC timestamp plus optional label),
holding the HTML pages, parsed JSON, per-ID request state, and a
`manifest.json`. Earlier snapshots are never overwritten. Its run options:

- `collection_mode`: `"none"` (default, no HTTP), `"new"` (new snapshot),
  or `"resume"` (continue an unfinished snapshot, retrying failed IDs).
- `snapshot_id`: `"latest"` or an exact identifier, for resume, rebuild, and inspection.
- `rebuild_csv` / `rebuild_from`: regenerate `equipments.csv` and
  `equipment_urls.csv` in `interim/scraping/<snapshot_id>/` from the stored
  JSON or by re-parsing the stored HTML. Rebuilding never changes the snapshot.
- `inspect_source`: inspect the selected snapshot's tables or the configured inputs.

To process a snapshot in notebooks 02 and 03, point `inputs.services` and
`inputs.equipment_urls` to that snapshot's tables in `interim/scraping/`.

New geocoding requests require `provider = "google"` or `"nominatim"` in
notebook 02. Requests have an initial budget of five per execution. Matching
coordinates are reused by ID and address. Errors and unresolved locations
remain explicit; changing the selection does not automatically request coordinates.

Review the source portal's terms before collection. The public Nominatim
service has a [specific usage policy](https://operations.osmfoundation.org/policies/nominatim/),
including a maximum of one request per second and bulk-use restrictions.
Use a suitable service or local instance for large collections. Google requests
may incur charges. Follow provider storage, use, and attribution requirements.
